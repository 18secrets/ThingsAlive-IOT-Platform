# Q08S — Signal binding layer

Attach: contract core (G01–G14 + §1 conventions) + §2, §2A.
Read: `docs/ai/REPO_MAP.md`, then only these modules — `projection`, `telemetry`, `equipment`,
`catalog` (equipment class profile and signal alias), `device-catalog`, `equipment-template`,
`inventory`, and the input-resolution path in `prediction`. Nothing else; if you need a file
outside this list, stop and say which and why.

Runs after Q00. Can run in parallel with A0 and Q21A. **Blocks Q21C, and every formula.**

```text
Implement Q08S only. This closes the gap between "a reading arrived" and "this equipment
has this signal", which every physics calculation, prediction input and readiness answer
depends on. Do not rebuild telemetry ingest, the projections or the catalog.

WHAT EXISTS, and must be preserved. sensor_map_projection is a read-only mirror of the
upstream sensor map, keyed (source_system, external_id), carrying imei, signal, sensor_name,
unit and tenant_id. Telemetry ingest uses it to resolve a tenant from an IMEI, and
telemetry_reading is keyed by IMEI plus a signal string from the payload. equipment_profile
holds 2.0's own attributes beside equipment_projection. equipment_class_profile declares
expected_signals per class. signal_alias maps upstream names to canonical signals.
device_inventory records which device is claimed onto which equipment.

WHAT device-catalog AND equipment-template ALREADY PROVIDE, which this layer JOINS TO and
must not duplicate.

  sensor is the sensor DEFINITION, with parameter_specs carrying parameter, unit, min, max
  and normal range. It is the shared contract's sensor_definition_version under another
  name. Add sensor_instance referencing sensor.id — an instance is a definition fitted at a
  position on one equipment, with its serial, install date, calibration requirement and
  status. Do NOT create a second sensor definition table and do NOT add columns to sensor,
  sensor_category or tool_mapping: they are Master Admin master data owned by device-catalog.
  A sensor's measurement range is an instrument limit. It is not a plausible operating range
  and it is never an alarm threshold; keep those three as separate fields and never derive
  one from another.

  tool_mapping is the EXPECTED CHANNEL LIST for a device profile: mapped_sensors says which
  sensors, and which of their parameters, a tool exposes. device_inventory.tool_mapping_id
  ties a registered device to one. So discovery has two independent sources — what the
  profile says the device SHOULD expose, and what sensor_map_projection says upstream
  ACTUALLY maps — and the difference between them is the useful output. Return three sets,
  never one merged list: matched, expected-but-absent, and present-but-unmapped. An
  expected channel that never arrives is a commissioning fault; an unmapped channel that
  keeps arriving is a mapping someone has not finished.

  equipment_template supplies SCALAR PARAMETERS rather than signals —
  fuel_tank_capacity_liters feeds the usable-fuel runtime calculation,
  service_interval_hours feeds the service forecast. A formula's inputs are signals AND
  approved parameters, and only the first come from telemetry. Carry an approved parameter
  reference on the equipment alongside its bindings, sourced from the template as an
  UNCONFIRMED proposal until someone with the right capability approves it. A template
  value that was never confirmed is parameters_required, not a default. Do not copy
  template fields onto equipment as plain columns; a template revision must not silently
  rewrite a machine's approved tank capacity.

  None of sensor, sensor_category, tool_mapping or equipment_template has a spec file today.
  Q08S's own tests must therefore cover the joins it relies on, not assume them.

WHAT IS MISSING. Nothing states that a particular signal is bound to a particular equipment.
Equipment-to-signal is inferred at query time through the device claim and a string match on
the reading's signal name. That fails on a machine with two probes of the same kind, on a
sensor replaced mid-history, on a unit that differs per device, and on an ECU-derived value
with no physical sensor — all four of which are in the shared fixture set. It also makes
absence unreadable: no reading for coolant_temp_c could mean not fitted, not mapped, or fitted
and silent, and readiness cannot honestly distinguish them.

THE SHAPE. Follow the precedent already set by equipment_projection and equipment_profile:
the mirror stays upstream-owned and untouched, and 2.0 owns a versioned table beside it.
Do not add columns to sensor_map_projection — a 2.0 column inside a mirror leaves the next
full reconcile unable to tell upstream drift from a local edit.

1. signal_binding_version, tenant-owned, covered by RLS, with a tenant-inclusive FK.
   Fields: equipment (source_system + external_id), signal_key (canonical), measurement_role
   drawn from the class's expected_signals, component_id?, origin = physical | ecu_derived |
   virtual, source imei? + channel/sensor_name?, canonical unit, unit_transform_version,
   calibration_version_id?, valid_from / valid_to as a half-open interval, expected_period,
   freshness_policy, quality_policy, status, and discovered_from (the projection row it came
   from, nullable). Exactly one PRIMARY binding per (tenant, equipment, signal_key,
   component, instant): two candidate sensors require an explicit choice and must never be
   silently averaged. Overlapping validity for the same primary key is refused by a
   constraint, not by application code.

2. calibration_version: method = identity | two_point | multipoint, raw and reference points
   with their units, performed/effective/expiry times, certificate ref?, uncertainty?,
   approved_by. Identity is permitted ONLY with an explicit approved factory or ECU basis
   recorded; it is never an automatic default. Transform order is fixed and documented:
   decode channel, approved engineering scale and offset, unit conversion, then optional
   residual calibration defined in canonical units. No undocumented double scaling. Add an
   allowlisted unit conversion registry with dimensional checks; Fahrenheit/Celsius offsets
   are a test case, not a multiplication.

3. Discovery, which proposes and never activates. For each device claimed onto an equipment,
   read BOTH its tool_mapping (through device_inventory.tool_mapping_id, expanding
   mapped_sensors to sensors and their parameter_specs) AND its sensor_map_projection rows,
   resolve upstream names through signal_alias, and produce PROPOSED bindings with their
   evidence and the source that supports each one. A proposal names the role it would satisfy
   on that equipment's class. It is not a binding until a person with the right capability
   confirms it. This is the backend behind the Add Machine screen's "Save Device & Discover
   Signals" step in both consoles, so return what that screen needs: proposed role, source,
   unit, confidence basis, and what is still unmatched.

4. Coverage and readiness, the primitive every later layer consumes. For an equipment,
   compare its class's REQUIRED expected_signals against active bindings and return, per the
   Operational / Analytical / Prediction grouping of G04, each item as Ready, Pending or
   Blocked with its reason: signal_unbound, mapping_required, calibration_expired,
   calibration_unknown, stale, unit_unresolved, no_primary_selected. Never collapse these
   into one value. An unbound required signal is Blocked, not silent.

5. Resolution at read time: resolveBinding(imei, signal, event_time) returns the binding
   version in force AT EVENT TIME, so a sensor replaced last month does not reattribute last
   year's readings. Scoring, physics and prediction resolve inputs by ROLE through bindings
   rather than by string-matching telemetry_reading.signal. Leave telemetry ingest itself
   unchanged; it keeps resolving tenant from IMEI as it does today.

6. Backfill, honestly labelled. Generate bindings for existing data from current projection
   rows, valid_from set to the earliest reading for that IMEI and signal, status
   discovered_unreviewed. Nothing existing breaks, and nothing claims to have been reviewed.
   A separate migration test asserts the backfill is idempotent and reversible.

Routes: GET /equipment/{id}/signal-bindings; POST /equipment/{id}/signal-bindings;
POST /signal-bindings/{id}/revisions; POST /equipment/{id}/discover-signals (proposals only);
GET /equipment/{id}/signal-coverage; POST /calibrations/preview; POST /calibrations/{id}/approve
behind calibration.approve. If-Match and idempotency keys throughout. Capability
signal.mapping.write, mapped to an existing equivalent if one is already defined.

Emit signal.binding.changed and calibration.changed transactionally with the write, through
the existing outbox, so readiness and context invalidate without deleting provenance.

Tests: two temperature probes on one composite machine bound to different components and
roles; an ECU-derived signal with no sensor instance; a device whose tool_mapping expects a
channel that never arrives, and one that receives a channel the mapping does not expect, each
reported in its own set rather than merged; a sensor_instance pointing at a device-catalog
sensor definition rather than a duplicated one; an unconfirmed equipment_template tank
capacity reporting parameters_required instead of being used as a default; a sensor replaced
mid-history, with a reading from before the swap still resolving to the old binding;
Fahrenheit source against a Celsius canonical unit; a second candidate sensor refused until a
primary is chosen; overlapping validity refused; a required signal unbound reporting Blocked
rather than absent; cross-tenant binding reference refused under the real application DB role;
backfill idempotent. No upstream writes anywhere — assert it.
```
