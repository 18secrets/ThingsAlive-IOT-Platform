## Runtime

NestJS 11, PostgreSQL 16, TypeORM migrations. `setGlobalPrefix('api')` + URI versioning, so
every route serves under `/api/v1`. Tests: Jest, `npm test`; type check `npm run lint`
(`tsc --noEmit`). No Python service exists in this repository — the `things-alive-logic`
modules the layer prompts reference (`physics.py`, `prediction.py`, `agents.py`,
`ta_logic/ml.py`) are **not present**, here or in the kit.

## Queue and jobs

`src/events/domain-event.entity.ts` is a PostgreSQL outbox, drained by a worker with no
tenant session. `shift_run` is a leased-job ledger. **No Redis and no RabbitMQ exist in this
repository.** The Railway topology document and task P0-16 assume RabbitMQ; that is an
unbuilt intention, not a running dependency. Per P00's own rule, the PostgreSQL outbox is
recorded as the mechanism — this is an answer, not a gap.

## Signal resolution, as it works today

`sensor_map_projection` mirrors the upstream sensor map keyed `(source_system, external_id)`
carrying `imei`, `signal`, `sensor_name`, `unit`, `tenant_id`. Telemetry ingest uses it for
exactly one purpose: resolving a tenant from an IMEI. `telemetry_reading` then stores the
signal as a **string taken from the payload**. Equipment-to-signal is therefore inferred at
query time, through the device claim in `device_inventory` plus a string match.

What `device-catalog` already provides, and Q08S must join to rather than duplicate:

- `sensor` is the **sensor definition** — `parameterSpecs` carries parameter, unit, min, max
  and normal range. This is the shared contract's `sensor_definition_version`. Q08S adds
  `sensor_instance` referencing `sensor.id`; it does not create a second sensor catalog.
- `tool_mapping` is the **expected channel list for a device profile**: `mappedSensors` says
  which sensors and which parameters a tool exposes. `device_inventory.tool_mapping_id` ties
  a registered device to one. Discovery therefore has two sources — what the profile says a
  device *should* expose, and what `sensor_map_projection` says upstream *actually* maps —
  and the difference between them is the useful part.
- `equipment_template` supplies **scalar parameters**, not signals: `fuelTankCapacityLiters`
  feeds the usable-fuel runtime calculation and `serviceIntervalHours` feeds the service
  forecast. A formula's inputs are signals *and* approved parameters, and only the first
  come from telemetry.

Neither `sensor`, `sensor_category`, `tool_mapping` nor `equipment_template` has a spec file.

There is no `signal_binding`, no `sensor_instance`, no `calibration_version`, no unit
conversion registry and no per-equipment declaration of which signals a machine actually
has. **This is the gap Q08S closes, and every formula, prediction input and readiness
answer depends on it.**

## Row-level security

Policies are named `tenant_isolation` and are `FORCE`d. The application role is `ta_app`:
unprivileged, not an owner, no `BYPASSRLS`. Tenant context is transaction-local. RLS is inert
under a superuser even with FORCE, so `test/db.ts` connects as `ta_app` — remove that and
every policy still exists, still reads correctly in `pg_policies`, and stops doing anything.
`test/rls-coverage.spec.ts` derives the protected set from entity metadata, so a new
tenant-owned table fails the suite the moment it is added.
